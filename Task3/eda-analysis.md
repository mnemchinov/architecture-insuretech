# Event-Driven архитектура для InsureTech

## Проблемы текущей архитектуры

### 1. Синхронное агрегирование данных от страховых компаний

**Описание проблемы:**
Сервис `ins-product-aggregator` при запросе от `core-app` или `ins-comp-settlement` синхронно запрашивает информацию из всех страховых компаний (текущее количество — 5, планируемое — 10), агрегирует данные и возвращает результат в рамках того же запроса.

**Влияние на систему:**
- При росте количества страховых компаний время отклика пропорционально увеличивается
- Сбой или задержка от одной страховой компании блокирует весь ответ
- Невозможность горизонтального масштабирования процесса агрегации

### 2. Периодический polling данных

**Описание проблемы:**
Сервисы хранят локальные реплики данных и обновляют их по расписанию:
- `core-app` запрашивает данные у `ins-product-aggregator` каждые **15 минут**
- `ins-comp-settlement` запрашивает данные раз в **сутки** (при формировании реестра)

**Влияние на систему:**
- Клиенты видят устаревшие данные до момента следующего обновления
- Неэффективное использование ресурсов при отсутствии изменений в данных страховых компаний
- Резкий всплеск нагрузки при одновременном обновлении несколькими сервисами

### 3. Ошибки взаимодействия с API страховых компаний

**Описание проблемы:**
Команда сталкивается с ошибками при взаимодействии с API страховых компаний, связанными с задержками ответов или недоступностью API.

**Влияние на систему:**
- Каскадные сбои при недоступности одной из страховых компаний
- Необходимость реализации повторных попыток (Retry) и защиты от сбоев (Circuit Breaker) на уровне `ins-product-aggregator`
- Сложность диагностики проблем в условиях синхронного взаимодействия

### 4. Нарушение SLA для B2B-партнёров

**Описание проблемы:**
Количество запросов от партнёров в периоды пиковой нагрузки достигает 250 RPS, что превышает заявленные 20 RPS и «сжирает» ресурсы приложения.

**Влияние на систему:**
- Деградация времени отклика для всех пользователей
- Невозможность гарантировать SLA для партнёров
- Риск репутационных потерь и оттока партнёров

## Риски при масштабировании

### Риск 1: Квадратичный рост нагрузки при увеличении страховых компаний

**Текущее состояние:** 5 страховых компаний
**Планируемое состояние:** 10 страховых компаний

При сохранении текущей архитектуры:
- Время отклика `ins-product-aggregator` увеличится в ~2 раза
- Количество потенциальных точек отказа увеличится с 5 до 10
- Нагрузка на сетевую инфраструктуру вырастет пропорционально

### Риск 2: Увеличение времени обработки данных

**Текущее состояние:** 5 компаний × ~1-2 сек на компанию = 5-10 сек полное время
**Планируемое состояние:** 10 компаний × ~1-2 сек = 10-20 сек полное время

Это приведёт к:
- Увеличению времени загрузки страниц
- Превышению SLA (SLA <= 99.9% availability)
- Снижению NPS и retention

### Риск 3: Проблема «двойной записи»

При оформлении страховки `core-app` должен:
1. Сохранить данные в БД
2. Отправить уведомление в `ins-comp-settlement`

При сбое после первого шага и до второго возникает несогласованность данных.

## Рекомендуемые события для Event-Streaming

### Событие 1: `product.updated`

| Параметр | Значение |
|----------|---------|
| Продюсер | `ins-product-aggregator` |
| Топик | `insurance-products` |
| Потребители | `core-app`, `ins-comp-settlement` |
| Данные | Обновлённая информация о продуктах и тарифах |
| Триггер | Изменение данных от любой страховой компании |

**Обоснование:** Заменяет polling от `core-app` (15 мин) и `ins-comp-settlement` (24 часа). Потребители получают актуальные данные в реальном времени.

### Событие 2: `policy.completed`

| Параметр | Значение |
|----------|---------|
| Продюсер | `core-app` |
| Топик | `policies` |
| Потребители | `ins-comp-settlement` |
| Данные | Информация об оформленной страховке |
| Триггер | Успешное оформление страховки |

**Обоснование:** Заменяет суточный polling от `ins-comp-settlement`. Данные о страховках передаются мгновенно после оформления.

### Событие 3: `settlement.completed`

| Параметр | Значение |
|----------|---------|
| Продюсер | `ins-comp-settlement` |
| Топик | `settlements` |
| Потребители | `ins-product-aggregator` |
| Данные | Результат взаиморасчётов со страховыми компаниями |
| Триггер | Завершение расчётов |

**Обоснование:** Обеспечивает асинхронную передачу данных о взаиморасчётах без синхронного запроса.

## Решение по паттерну Transactional Outbox

### Рекомендация: Использовать паттерн Transactional Outbox

**Обоснование:**

1. **Решение проблемы «двойной записи»**
   При оформлении страховки `core-app` должен сохранить данные в БД и опубликовать событие `policy.completed`. Без Transactional Outbox возможна несогласованность: данные сохранены, но событие не отправлено.

2. **Гарантия доставки событий**
   Из теории: события должны быть долговечны и воспроизводимы. Transactional Outbox обеспечивает запись события в ту же транзакцию, что и бизнес-данные.

3. **Предотвращение каскадных сбоев**
   При недоступности брокера сообщений данные сохраняются в Outbox-таблицу и будут отправлены после восстановления.

### Компоненты решения

| Компонент | Описание |
|-----------|---------|
| Outbox-таблица | Хранится в той же БД, что и бизнес-данные. Запись в рамках единой транзакции. |
| Outbox API | Структура таблицы — контракт события. Применим подход API First. |
| Передатчик сообщений | Реализация: Polling publisher или Transaction log tailing (CDC через Debezium). |

### Реализация передатчика: Polling publisher

**Выбор обоснован:**
- Простота реализации и поддержки
- Отсутствие зависимости от специфичных механизмов конкретной СУБД
- Возможность повторной отправки сообщений при сбоях

**Конфигурация:**
- Интервал опроса: 1-5 секунд
- Стратегия обработки: пометка отправленных сообщений (не удаление) для возможности повторной отправки

## Сложности перехода на Event-Driven архитектуру

1. **Итоговая согласованность**
   Асинхронное взаимодействие подразумевает eventual consistency. Система и процессы должны учитывать возможность временного расхождения данных.

2. **Идемпотентность обработки событий**
   Передатчик сообщений может опубликовать событие более одного раза (сбой после публикации, но до фиксации). Потребители должны быть идемпотентными.

3. **Дополнительная сложность**
   Требуется внедрение брокера сообщений, Outbox-таблиц, передатчика. Увеличивается количество компонентов для поддержки.

4. **Необходимость персистентного хранилища**
   Transactional Outbox требует наличия БД. Для сервисов без БД потребуется дополнительное хранилище.

## Итоговая архитектура

### Изменения в диаграмме контейнеров

| Элемент | Изменение |
|---------|-----------|
| Добавлен Event Broker | Apache Kafka / Yandex Cloud Managed Service for Apache Kafka® |
| Заменены REST-запросы polling | Асинхронные события через Kafka |
| Добавлены Outbox-таблицы | В сервисах `core-app`, `ins-product-aggregator` |
| Добавлен передатчик сообщений | Компонент для чтения из Outbox и отправки в Kafka |

### Потоки данных после миграции

```
ins-product-aggregator
  ├── [product.updated] ──→ Kafka ──→ core-app
  │                                    └── получает данные в реальном времени
  └── [product.updated] ──→ Kafka ──→ ins-comp-settlement
                                          └── получает данные без суточного polling

core-app
  ├── [policy.completed] ──→ Kafka ──→ ins-comp-settlement
  │                                     └── получает данные сразу после оформления
  └── [Outbox Table] ──→ Передатчик ──→ Kafka

ins-comp-settlement
  └── [settlement.completed] ──→ Kafka ──→ ins-product-aggregator
```

## Рекомендации по внедрению

1. **Фаза 1: Минимальное внедрение**
   - Внедрить Event Broker (Kafka)
   - Настроить событие `product.updated` от `ins-product-aggregator`
   - Потребители: `core-app`, `ins-comp-settlement`
   - Убрать polling

2. **Фаза 2: Событие оформления страховки**
   - Внедрить Transactional Outbox в `core-app`
   - Настроить событие `policy.completed`
   - Потребитель: `ins-comp-settlement`
   - Убрать суточный polling от `ins-comp-settlement`

3. **Фаза 3: Расширение**
   - Подключение новых страховых компаний
   - Мониторинг и оптимизация
