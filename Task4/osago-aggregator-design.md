# Архитектура сервиса ОСАГО-агрегатора

## 1. Описание сценария работы

### Пользовательский путь
1. Клиент заполняет заявку на ОСАГО через веб-приложение (данные автомобиля, водителя)
2. Веб-приложение отправляет запрос в `core-app`
3. `core-app` создаёт асинхронную заявку в `osago-aggregator`, получает ID для отслеживания
4. `osago-aggregator` параллельно отправляет запросы во все страховые компании (5+)
5. По мере поступления ответов от страховых, `osago-aggregator` пушит результаты в `core-app` через REST callback
6. `core-app` передаёт предложения в веб-приложение через SSE (Server-Sent Events)
7. Клиент видит предложения от каждой страховой компании сразу, как только они приходят

### Требования бизнеса
- **Максимальное время ожидания:** 60 секунд
- **Одновременные пользователи:** до 2500 человек
- **Отображение результатов:** real-time (по мере поступления от страховых)

---

## 2. Архитектурные решения

### 2.1 Выделенный сервис `osago-aggregator`
- **Технология:** Kotlin, SpringBoot
- **Назначение:** Оркестрация запросов к страховым компаниям
- **Хранилище:** PostgreSQL (отдельная БД `osago-aggregator-db`)

### 2.2 Зачем нужно отдельное хранилище данных?
1. **Координация множественных экземпляров сервиса** — при горизонтальном масштабировании несколько экземпляров `osago-aggregator` могут обрабатывать одну заявку
2. **Идемпотентность** — предотвращение дублирования запросов к страховым компаниям
3. **Сохранение статуса заявки** — возможность восстановления после сбоя
4. **Кэширование результатов** — избегание повторных запросов к страховым

### 2.3 API для core-app
| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| POST | `/api/osago/requests` | Создание заявки, возврат ID |
| GET | `/api/osago/requests/{id}/status` | Проверка статуса (если SSE недоступен) |
| Callback | `POST /api/osago/callback/{requestId}` | Получение результатов от осого-агрегатора |

### 2.4 Интеграция между core-app и osago-aggregator
- **Основной канал:** REST (асинхронный)
- **Callback:** REST для push-уведомлений о результатах
- **Альтернатива:** SSE для веб-приложения (core-app → web)

### 2.5 Интеграция с веб-приложением
- **Технология:** Server-Sent Events (SSE)
- **Эндпоинт:** `GET /api/osago/stream/{requestId}`
- **Преимущество:** Односторонний поток данных, низкая задержка

## 3. Паттерны отказоустойчивости

### 3.1 Rate Limiter (Ограничение частоты запросов)
**Где применяется:**
- core-app → osago-aggregator
- osago-aggregator → страховые компании

**Конфигурация:**
```yaml
rate-limiter:
  requests-per-second: 100  # Для защиты внешних API страховых
  burst-size: 200
  core-to-osago:
    requests-per-second: 500
    burst-size: 1000
```

**Обоснование:** Защита внешних API страховых компаний от перегрузки (2500 RPS пиковая нагрузка)

### 3.2 Circuit Breaker (Автоматическое отключение при сбоях)
**Где применяется:**
- core-app → osago-aggregator
- osago-aggregator → страховые компании

**Конфигурация:**
```yaml
circuit-breaker:
  failure-threshold: 5        # Количество ошибок до открытия
  failure-rate-threshold: 50% # Процент ошибок до открытия
  wait-duration: 30s          # Время ожидания перед half-open
  per-call-timeout: 5s        # Таймаут на один вызов
```

**Обоснование:** Изоляция сбоев одной страховой компании не должна влиять на обработку запросов к другим

### 3.3 Retry (Повтор неудачных запросов)
**Где применяется:**
- core-app → osago-aggregator
- osago-aggregator → страховые компании

**Конфигурация:**
```yaml
retry:
  max-attempts: 3            # Максимальное количество попыток
  backoff-initial: 1s        # Начальная задержка
  backoff-max: 10s           # Максимальная задержка
  backoff-multiplier: 2      # Коэффициент экспоненциальной задержки
  retry-on:                  # Какие ошибки требуют повтор
    - timeout
    - connection-refused
    - 5xx-server-errors
```

**Обоснование:** Временные сетевые сбои не должны приводить к отказу в обслуживании

### 3.4 Timeout (Ограничение времени ожидания)
**Где применяется:**
- core-app → osago-aggregator
- osago-aggregator → страховые компании

**Конфигурация:**
```yaml
timeout:
  osago-aggregator: 60s      # Общее время ожидания (бизнес-требование)
  per-insurer: 10s           # Таймаут на одну страховую компанию
  core-app: 5s               # Таймаут при создании заявки
```

**Обоснование:** Соответствие бизнес-требованию (максимум 60 секунд ожидания)

### 3.5 Bulkhead (Изоляция ресурсов)
**Где применяется:**
- osago-aggregator → страховые компании (для каждой страховой отдельно)

**Конфигурация:**
```yaml
bulkhead:
  per-insurer:
    max-concurrent-calls: 100  # Максимум параллельных запросов к одной страховой
    max-wait-duration: 2s      # Максимальное время ожидания в очереди
  total-max-concurrent: 500    # Общее ограничение на все страховые
```

**Обоснование:** 
- Предотвращение "утонения" ресурсов при сбое одной страховой компании
- Изоляция сбоев — отказ одной страховой не влияет на обработку запросов к другим
- Равномерное распределение нагрузки между страховыми компаниями

## 4. Обработка частичных результатов

### 4.1 Сценарий частичного сбоя
Если одна или несколько страховых компаний не ответили в течение таймаута:
1. `osago-aggregator` продолжает ждать ответы от остальных страховых
2. По истечении общего таймаута (60 секунд) возвращается **доступное множество результатов**
3. Веб-приложение отображает только полученные предложения
4. В интерфейсе отображается информация: "Получено 4 из 5 предложений"

### 4.2 Логика агрегации результатов
```java
public List<OsagoOffer> aggregateResults(OsagoRequest request, Duration timeout) {
    List<CompletableFuture<OsagoOffer>> futures = insuranceCompanies.stream()
        .map(company -> sendRequestAsync(company, request))
        .collect(Collectors.toList());
    
    return CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
        .orTimeout(timeout)
        .thenApply(v -> futures.stream()
            .filter(CompletableFuture::isDone)
            .map(CompletableFuture::join)
            .filter(Objects::nonNull)
            .collect(Collectors.toList())
        ).get();
}
```

### 4.3 Поведение при 100% сбое
Если ни одна страховая компания не ответила:
1. Возвращается пустой список предложений
2. Пользователю отображается сообщение: "Временно невозможно получить предложения от страховых компаний. Попробуйте позже"
3. Заявка сохраняется в статусе `PENDING` для возможного повторного опроса

## 5. Масштабирование

### 5.1 Горизонтальное масштабирование osago-aggregator
- **Минимальное количество экземпляров:** 3 (для отказоустойчивости)
- **Максимальное количество экземпляров:** 20 (при пиковой нагрузке 2500 RPS)
- **Критерии масштабирования:**
  - CPU utilization > 70%
  - Memory utilization > 80%
  - Queue depth > 100 запросов на экземпляр

### 5.2 Координация через БД
При множественных экземплярах используется механизм оптимистичной блокировки:
```sql
INSERT INTO osago_requests (id, status, created_at)
VALUES (?, ?, ?)
ON CONFLICT (id) DO NOTHING;

-- Только один экземпляр сервиса получит строку
-- Остальные будут проигнорированы (идемпотентность)
```

## 6. Мониторинг и метрики

### 6.1 Ключевые метрики
| Метрика | Описание | Порог алерта |
|---------|----------|--------------|
| `osago_requests_total` | Общее количество заявок | - |
| `osago_request_duration_seconds` | Время обработки заявки | P95 > 30s |
| `osago_insurer_response_time` | Время ответа страховой | P99 > 8s |
| `osago_circuit_breaker_state` | Состояние Circuit Breaker | OPEN |
| `osago_bulkhead_queue_size` | Размер очереди Bulkhead | > 80% |

### 6.2 Логи
- **INFO:** Создание заявки, получение результата от страховой
- **WARN:** Повтор запроса (retry), срабатывание Rate Limiter
- **ERROR:** Открытие Circuit Breaker, таймаут опроса

---

## 7. Заключение

Архитектура ОСАГО-агрегатора обеспечивает:
- ✅ Время ответа ≤ 60 секунд (бизнес-требование)
- ✅ Обработку 2500 одновременных пользователей
- ✅ Отказоустойчивость при сбоях отдельных страховых компаний
- ✅ Real-time отображение результатов для клиента
- ✅ Масштабируемость через горизонтальное масштабирование

Все 5 паттернов отказоустойчивости (Rate Limiting, Circuit Breaker, Retry, Timeout, Bulkhead) применены для обеспечения надёжности системы.
