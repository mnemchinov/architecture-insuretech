# Технологическая архитектура InsureTech (to-be)

## Описание решения

Данная архитектура разработана для обеспечения следующих требований бизнеса:
- **RTO (Recovery Time Objective)**: ≤ 45 минут
- **RPO (Recovery Point Objective)**: ≤ 15 минут
- **Доступность**: 99,9%
- **Одинаковое время загрузки** для пользователей из всех регионов РФ

---

## Ключевые решения

### 1. Стратегия Active-Active с георезервированием

**Выбрано**: Два независимых кластера Kubernetes в разных ЦОД (Москва и Санкт-Петербург), работающих одновременно.

**Обоснование**:
- Оба кластера обрабатывают трафик, что обеспечивает максимальную утилизацию ресурсов
- При сбое одного ЦОД GSLB автоматически перенаправляет весь трафик на второй ЦОД
- Отсутствие простоя — время переключения определяется только временем обнаружения сбоя (health-check)

**Альтернативы**:
- *Active-Passive*: Не подходит, так как требует больше времени на "прогрев" резервного узла и не обеспечивает оптимальной утилизации ресурсов
- *Cold Standby*: Недопустимо — время развёртывания превышает RTO 45 минут

### 2. Независимые кластеры Kubernetes (vs растянутый кластер)

**Выбрано**: Два независимых кластера Kubernetes в разных ЦОД.

**Обоснование**:
- **Изоляция при сбое**: Полный сбой одного ЦОД не влияет на второй кластер
- **Независимое масштабирование**: Каждый кластер можно масштабировать независимо под нагрузку региона
- **Простота администрирования**: Стандартные инструменты K8s без сложных кастомизаций
- **Защита от сетевых проблем**: Не зависит от стабильности канала связи между ЦОД

**Почему не растянутый кластер**:
- Растянутые кластеры требуют низколатентного канала связи (< 5 мс)
- Сложность управления etcd при высокой задержке между ЦОД
- Высокий риск "split-brain" при потере связи между площадками

### 3. База данных: PostgreSQL + Patroni

**Конфигурация**:
- Внутри ЦОД: 1 Master + 2 синхронных реплики (синхронная репликация)
- Между ЦОД: Асинхронная репликация (Patroni + pgBackRest)

**Как достигаются требования**:
- **RPO ≤ 15 мин**: Асинхронная репликация с задержкой не более 15 минут
- **RTO ≤ 45 мин**: Patroni автоматически выбирает нового лидера за < 30 секунд
- **99,9% доступность**: Синхронная репликация внутри ЦОД обеспечивает отсутствие потери данных при сбое узла

**Почему Patroni**:
- Автоматический failover без участия человека
- Интеграция с etcd для хранения состояния кластера
- Поддержка pgBackRest для резервного копирования

### 4. Глобальный балансировщик нагрузки (GSLB)

**Решение**: DNS-based GSLB с health-check.

**Функции**:
- Гео-маршрутизация: Пользователи направляются к ближайшему ЦОД
- Health-check: Постоянный мониторинг доступности обоих ЦОД
- Автоматический failover: При недоступности одного ЦОД весь трафик идёт на второй

**Алгоритм**:
1. Пользователь запрашивает DNS-имя
2. GSLB определяет геолокацию пользователя
3. Возвращает IP ближайшего доступного ЦОД
4. При сбое одного ЦОД — возвращает IP второго

### 5. Кэширование: Redis Cluster (Sentinel)

**Конфигурация**: 3 узла (1 Master + 2 Sentinels) в каждом ЦОД.

**Назначение**:
- Кэширование часто запрашиваемых данных (продукты, тарифы, клиентские данные)
- Снижение нагрузки на PostgreSQL
- Уменьшение времени отклика для пользователей

### 6. Брокер сообщений: Kafka Cluster

**Конфигурация**: 3 брокера в каждом ЦОД + Kafka MirrorMaker для репликации между ЦОД.

**Назначение**:
- Асинхронная коммуникация между сервисами (Event-Driven архитектура)
- Буферизация нагрузки при пиках
- Репликация событий между ЦОД для консистентности данных

### 7. Мониторинг: Prometheus + Grafana

**Назначение**:
- Сбор метрик со всех компонентов (K8s, PostgreSQL, Redis, Kafka, приложения)
- Визуализация и алертинг
- Отслеживание RTO/RPO в реальном времени

### 8. Централизованное логирование: ELK Stack / Loki

**Конфигурация**: Elasticsearch + Logstash + Kibana (или Prometheus Loki + Grafana) в каждом ЦОД с репликацией логов между ЦОД.

**Назначение**:
- Агрегация логов со всех подов, сервисов и инфраструктуры
- Централизованный поиск и анализ логов
- Отслеживание инцидентов и расследование сбоев
- Соответствие требованиям аудита и комплаенса
- Долгосрочное хранение логов (до 90 дней)

## План восстановления при сбое (Disaster Recovery Plan)

### Сценарий 1: Сбой узла в кластере K8s (ЦОД 1)
1. **Обнаружение**: Health-check K8s обнаруживает сбой пода (< 10 сек)
2. **Восстановление**: K8s автоматически перезапускает под на другом узле (< 1 мин)
3. **Время простоя**: Практически нулевое (пользователи не замечают)

### Сценарий 2: Сбой PostgreSQL Master (ЦОД 1)
1. **Обнаружение**: Patroni обнаруживает сбой Master (< 5 сек)
2. **Выбор нового лидера**: Patroni выбирает одну из реплик (< 10 сек)
3. **Переключение**: Новый Master принимает подключения (< 15 сек)
4. **Время простоя**: < 30 секунд (пользователи могут заметить кратковременную задержку)

### Сценарий 3: Полный сбой ЦОД 1 (Москва)
1. **Обнаружение**: GSLB обнаруживает недоступность ЦОД 1 (< 30 сек)
2. **Переключение трафика**: GSLB направляет весь трафик в ЦОД 2 (< 1 мин)
3. **Активация реплики БД**: Patroni в ЦОД 2 становится Master (асинхронная репликация уже активна)
4. **Восстановление**: Приложение в ЦОД 2 обрабатывает 100% нагрузки
5. **Время простоя**: < 2 минут (пользователи могут заметить кратковременную задержку)

### Сценарий 4: Сбой канала связи между ЦОД
1. **Обнаружение**: Мониторинг фиксирует потерю связи
2. **Работа в изоляции**: Оба ЦОД продолжают работать независимо
3. **Синхронизация**: При восстановлении канала — репликация накопленных изменений
4. **Влияние на пользователей**: Отсутствует (оба ЦОД активны)

## Оценка соответствия требованиям

| Требование | Целевое значение | Реализация | Статус |
|------------|------------------|------------|--------|
| RTO | ≤ 45 мин | < 2 мин (полный сбой ЦОД) | ✅ Выполнено |
| RPO | ≤ 15 мин | Асинхронная репликация с задержкой < 15 мин | ✅ Выполнено |
| Доступность | 99,9% | Active-Active + георезервирование | ✅ Выполнено |
| Скорость загрузки | Одинаковая для всех регионов | GSLB + гео-маршрутизация | ✅ Выполнено |

## Экономическое обоснование

**Затраты**:
- 2 ЦОД с полным набором компонентов (2x K8s, 2x PostgreSQL, 2x Redis, 2x Kafka)
- GSLB (можно использовать облачный или самописное решение на базе Keepalived + DNS)
- Канал связи между ЦОД (выделенная линия или VPN)

**Обоснование**:
- Потеря 500 тыс. ₽ в час простоя × 45 мин = **375 тыс. ₽** при одном сбое
- При 12 сбоях в год (статистика для систем без HA) = **4.5 млн ₽/год**
- Стоимость реализации HA: ~1.5-2 млн ₽/год (инфраструктура + поддержка)
- **Экономия**: ~2.5 млн ₽/год

## Примечания

1. **Шардирование БД**: Не требуется при текущем объёме данных (50 ГБ). Будет рассмотрено при росте данных > 500 ГБ.
2. **Резервное копирование**: pgBackRest с хранением бэкапов в S3 (отдельно от ЦОД).
3. **Безопасность**: TLS для всех соединений между компонентами, WAF перед GSLB.
4. **Масштабирование**: HPA настроен на основе метрик CPU и памяти (см. Task2).
